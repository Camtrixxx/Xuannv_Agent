# Xuannv Agent 开发计划：海淀三场景与架构演进

> 编制 2026-07（2026-07 修订）｜关联：[基于 10m 遥感数据底座的场景能力边界与应用方向](./基于%2010m%20遥感数据底座的场景能力边界与应用方向.md)

## 0. 本次修订要点（相对初版）

- **聚焦收敛**：主攻**北京市海淀区**；雅江/哈尔滨暂不投入新功能，代码保留可运行、不再是重心。
- **分工明确**：海淀模型推理**后续由外部 API 提供**（接口规格未定）。我们**只专注 agent 层**——意图、编排、聚合、报告、可视化；区域 service 逐步退化为薄 adapter。
- **智能化方向已定**：agent 升级目标为 **LLM function-calling 规划器**（DeepSeek 已接入并实测可用）。
- **落地顺序**：先出"报告详情地图叠加"（见效快）→ 再做架构精简 → 再上 planner。
- **进度**：阶段一（地图叠加）✅；阶段二（架构精简）🔨 进行中（taxonomy 单一词表已落地）；**海淀三场景（A 片区综合体检 / B 建设扰动监测 / C 补绿优先区评分）均已上线并端到端验证**（124 项 pytest 全绿）。planner（阶段三）暂以确定性意图路由替代，留作后续版本。

## 1. 背景与目标

场景能力边界文档确立产品定位：**从"单任务出图工具"升级为"区域级生态与建设变化智能分析底座"**。本计划回答两个问题：

1. **近期做什么**：聚焦海淀，落地 3 个复合型场景（片区体检 / 建设扰动 / 压力评分）。
2. **架构怎么演进**：为"更聪明的 agent"（function-calling 规划、工具/技能、联网、外部数据）打好精简、可维护、易扩展的地基——**场景是验证架构的载体，架构是场景的复用底座**。

设计红线：**精简优先**。不预先堆叠六层框架，只在场景需要时"长"出对应能力；每步都保持行为可回归、测试全绿。

### 2.3 海淀数据实际（决定场景形态）

- 月份覆盖：**2025-12 ～ 2026-05**（≈6 个月，含月内多期 `20251201/20251212/...`）→ 做"短周期变化"，不承诺"近三年"。
- 任务：建筑物提取、道路提取、施工识别、土地利用分类、土地覆盖分类、水体提取。
- 数据形态：patch 级**结果 PNG（128×128）** + embedding 预览；无逐像素概率；system-models 推理未开放。
- 尺度：1 patch ≈ 1.28km × 1.28km ≈ **164 公顷** → 一个街道级 AOI 通常覆盖 4~20 个 patch。
- 后续接入方式：**模型推理走外部 API**（规格待定）。区域 service 按"薄 adapter + 数据访问层"设计，接口就绪即切换，不影响 agent 层。

## 3. 目标架构（精简版）

初版的六层框架偏重。本次收敛为**三个核心层 + 一个词表底座**，其余能力按场景需要再"长"出来：

```
┌───────────────────────────────────────────────────────────┐
│ 接入层  FastAPI：/api/report、/api/patches、/api/session    │
│         现有 /api/report 行为不破坏，前端零/极小改动           │
├───────────────────────────────────────────────────────────┤
│ 编排层  LangGraph Agent：意图 → 规划(planner 选技能) → 执行   │
│         → 报告。对话/追问/澄清逻辑保持现状                     │
├───────────────────────────────────────────────────────────┤
│ 技能层  Skill（场景=工具编排）                                │
│   region_checkup / change_monitor / priority_rank            │
├───────────────────────────────────────────────────────────┤
│ 工具层  Tool 原子能力（纯函数、可单测）                        │
│   aoi_cover  class_map  raster_stats  change_diff  score_rank │
├───────────────────────────────────────────────────────────┤
│ 数据访问层  Adapters（超时+重试+缓存）                         │
│   HaidianAPIClient（外部模型 API）│ 未来：POI / web_search    │
├───────────────────────────────────────────────────────────┤
│ 底座  taxonomy(单一词表 ✅) · config · SQLite 记忆             │
└───────────────────────────────────────────────────────────┘
```

### 3.1 核心设计决策

1. **taxonomy 单一词表**（✅ 已落地）：区域、任务、别名、月份覆盖、区域×任务映射全部收敛到 `agent/taxonomy.py`，其余模块只引用、不再各存一份。彻底消除 G5 漂移。
2. **数据访问层收口**：所有外部 HTTP（海淀 API、embedding-api、未来 POI/搜索）走带**超时+重试+缓存**的 client 基类；海淀 PNG→类别映射也在这层解决（G3）。上层拿结构化数据，感知不到来源抖动。
3. **agent 只碰 agent 层**：海淀模型推理交给外部 API；区域 service 退化为薄 adapter，接口一变只改 adapter。
4. **Skill = 场景封装 / Tool = 复用原子能力**：新场景 = 新增 skill + 注册，不改编排层；三场景共用同一批 tool。
5. **planner 用 LLM function-calling**：DeepSeek 暴露"可调工具/技能"，由模型按意图自主选择与编排，替换固定 if-else 路由——这是"真正的 agent"的落点。
6. **兼容优先**：`/api/report` 行为不破坏，新场景经意图识别自动路由，前端零/极小改动。

## 4. 海淀三场景定义

> 从能力边界文档 8 个场景中，按海淀（城市核心区、6 个月数据）挑选场景一、三、七，三者共用工具链且递进建设 G1→G2→评分层。

### 场景 A：片区综合体检（城市版）——建 AOI 聚合地基

- **问法**："帮我分析这个片区的绿地和硬化情况" / "生成这个范围的生态体检报告"（框选 AOI）
- **数据流**：AOI → 覆盖 patch 集合 → 逐 patch 取土地覆盖/水体结果 PNG → 颜色→类别映射 → 按 AOI 裁剪聚合 → **面积（公顷）与占比** → 高硬化低绿地 patch 标记 → 体检报告
- **报告主语**：绿地率 / 硬化率 / 水面率 / 各类面积公顷数 + 空间分布图 + 问题区初筛
- **工具**：`aoi_cover`、`class_map`、`raster_stats`
- **边界**：不识别单栋建筑用途；面积为 10m 尺度估算值

### 场景 B：建设扰动短周期监测——建变化检测地基

- **问法**："这个片区最近半年哪里在施工/新增硬化？" / "对比 2025年12月 和 2026年5月 的变化"
- **数据流**：AOI → patch 集合 → 取**两期**结果 PNG → 逐像元 diff → 变化斑块提取 → 变化面积/位置清单 → 扰动强度排序 → 监测报告
- **报告主语**：变化斑块地图 + "哪里变了、变了多少公顷、朝什么方向变" + 巡查建议清单
- **工具**：`change_diff`（两期栅格类别转换矩阵 + 连通斑块）
- **可视化**：地图叠加已支持单期 overlay；两期对比届时加**卷帘（swipe）控件**
- **边界**：6 个月短周期；提供线索不做违建认定

### 场景 C：高硬化低绿地压力与补绿优先区——建评分/排序层（面向决策）

- **问法**："哪些片区硬化率高、绿地率低？" / "哪里适合优先补绿？"
- **数据流**：复用 A 聚合 + B 趋势 → patch 级复合评分（硬化率↑ + 绿地率↓ + 距水/绿远 + 近期硬化仍增）→ 压力分级图 + **补绿优先区清单**
- **报告主语**：压力 TOP-N 排名 + 每区"为什么上榜" + 行动建议（服务城市更新/花园城市）
- **工具**：`score_rank`（多因子加权，权重可配）
- **边界**：热岛为代理指标（无热红外反演）；评分是初筛不是工程结论

**递进关系**：A 建聚合 → B 建变化 → C 组合评分。做完三者，能力边界文档其余场景均为工具重组。
