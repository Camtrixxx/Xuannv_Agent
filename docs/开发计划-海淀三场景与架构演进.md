# Xuannv Agent 开发计划：海淀三场景与架构演进

> 编制日期：2026-07　｜　关联文档：[基于 10m 遥感数据底座的场景能力边界与应用方向](./基于%2010m%20遥感数据底座的场景能力边界与应用方向.md)

## 1. 背景与目标

场景能力边界文档确立了产品新定位：**从"单任务出图工具"升级为"区域级生态与建设变化智能分析底座"**。本计划回答两个问题：

1. **近期做什么**：聚焦北京市海淀区，落地 3 个复合型场景。
2. **架构怎么演进**：为"更聪明的 agent"（联网搜索、外部数据、skill 封装）打好高可用、可扩展、易维护的地基——场景是验证架构的载体，架构是场景的复用底座。

### 2.3 海淀数据实际（决定场景形态）

- 月份覆盖：**2025-12 ～ 2026-05**（≈6 个月，含月内多期 `20251201/20251212/...`）→ 做"短周期变化"，不承诺"近三年"。
- 任务：建筑物提取、道路提取、施工识别、土地利用分类、土地覆盖分类、水体提取。
- 数据形态：patch 级**结果 PNG（128×128）** + embedding 预览；无逐像素概率；system-models 推理未开放。
- 尺度：1 patch ≈ 1.28km × 1.28km ≈ **164 公顷**（128×128 像元 × 100㎡）→ 一个街道级 AOI 通常覆盖 4~20 个 patch。

## 3. 目标架构

### 3.1 分层视图

```
┌─────────────────────────────────────────────────────────┐
│ 接入层  FastAPI (/api/v1)：report、patches、sessions、docs │
├─────────────────────────────────────────────────────────┤
│ 编排层  LangGraph Agent：意图 → 规划(选技能) → 执行 → 报告   │
│         对话/追问/澄清逻辑保持现状，新增 planner 选 skill      │
├─────────────────────────────────────────────────────────┤
│ 技能层  Skill Registry（声明式注册）                        │
│   region_checkup / change_monitor / priority_rank / ...   │
│   未来：web_search、external_data_overlay、buffer_analysis │
├─────────────────────────────────────────────────────────┤
│ 工具层  Tool 原子能力（纯函数优先，可单测）                    │
│   aoi_cover  raster_stats  class_map  change_diff          │
│   score_rank  basemap  llm  geo(面积/缓冲)                  │
├─────────────────────────────────────────────────────────┤
│ 数据访问层  Region/Data Adapters（重试+缓存+熔断）            │
│   AEFClient │ EmbeddingAPIClient(harbin/haidian) │ 未来:POI │
├─────────────────────────────────────────────────────────┤
│ 基础设施  taxonomy(单一词表) config 日志/追踪 SQLite(WAL)     │
└─────────────────────────────────────────────────────────┘
```

### 3.2 核心设计决策

1. **Skill = 场景的封装单元**。每个 skill 声明：`name / description / input_schema / supported_regions / tools_used / report_template`。编排层 planner 根据意图选 skill（先规则映射，后续升级为 LLM function-calling 式选择）。新场景 = 新增一个 skill 文件 + 注册，不改编排层。
2. **Tool = 可复用原子能力**，无状态、纯函数优先（好测试、好组合）。三个场景共用同一批 tool，这是"底座"的技术含义。
3. **数据访问层收口**：所有外部 HTTP（AEF、embedding-api、未来 POI/搜索）统一走带**超时+重试+熔断+磁盘缓存**的 client 基类；上层拿到的是结构化数据，感知不到来源抖动。海淀 PNG→类别映射也在这层解决（G3）。
4. **词表收敛为 `agent/taxonomy.py` 单一来源**（G5）：区域、任务、别名、月份覆盖、区域×任务矩阵，其余模块只引用。
5. **兼容优先**：现有 `/api/report` 行为不破坏；新场景通过意图识别自动路由，同一入口。前端零改动或极小改动（延续既往约定）。

### 3.3 高可用 / 可扩展 / 易维护 对照表

| 目标 | 手段（近期可落地） |
| --- | --- |
| 高可用 | systemd 托管 + 自动重启（替代 nohup）；uvicorn 多 worker（SQLite 开 WAL）；数据访问层统一重试/超时/熔断；PNG 与聚合结果磁盘缓存；`/api/health` 增加依赖探测（AEF、embedding-api、LLM） |
| 可扩展 | skill/tool 注册表；数据访问层 adapter 模式（新数据源=新 adapter）；LLM Provider 抽象已存在，保留多供应商可能 |
| 易维护 | taxonomy 单一词表；app.py 路由拆分（routes/ 模块化）；tool 层纯函数 + pytest 全覆盖；结构化日志（每次 run 记录 intent/route/skill/耗时/llm_status），排障可追溯 |

### 3.4 未来能力如何"长"进来（预留接口）

- **联网搜索**：新增 `web_search` tool + 数据访问层一个 SearchClient；chat/报告解读节点可引用搜索结果做背景补充。不动编排骨架。
- **外部数据（POI/路网/矢量）**：新增 DataProvider adapter + `buffer_analysis` tool（届时引入 shapely）；场景升级为"外部数据定位对象、底座解释状态与变化"（对应能力边界文档第五章）。
- **更多 skill**：能力边界文档其余 5 个场景（蓝绿韧性、水体缓冲带、生态退化、山前敏感、修复优先）都是现有 tool 的重新组合，逐个注册即可。

## 4. 海淀三场景定义

> 从能力边界文档 8 个场景中，按海淀（城市核心区、6 个月数据）适配挑选：场景一、三、七。三者共用工具链且递进建设 G1→G2→评分层。

### 场景 A：片区综合体检（城市版）——建 AOI 聚合地基

- **用户问法**："帮我分析这个片区的绿地和硬化情况" / "生成这个范围的生态体检报告"（框选 AOI）
- **数据流**：AOI → 覆盖 patch 集合（现有 patch 检索复用）→ 逐 patch 取土地覆盖/水体结果 PNG → 颜色→类别映射 → 按 AOI 裁剪聚合 → **面积（公顷）与占比** → 高硬化低绿地 patch 标记 → 体检报告
- **报告主语**（从"精度指标"转向"底数"）：绿地率 / 硬化率 / 水面率 / 各类面积公顷数 + 空间分布图 + 问题区初筛
- **建成工具**：`aoi_cover`、`class_map`、`raster_stats(面积换算)`
- **明确边界**：不识别单栋建筑用途；面积为 10m 尺度估算值

### 场景 B：建设扰动短周期监测——建变化检测地基

- **用户问法**："这个片区最近半年哪里在施工/新增硬化？" / "对比 2025年12月 和 2026年5月 的变化"
- **数据流**：AOI → patch 集合 → 取**两期**结果 PNG（土地覆盖 + 施工识别）→ 逐像元 diff → 变化斑块提取（新增硬化、绿地转硬化、新增施工）→ 变化面积/位置清单 → 扰动强度排序 → 监测报告
- **报告主语**：变化斑块地图 + "哪里变了、变了多少公顷、朝什么方向变" + 巡查建议清单
- **建成工具**：`change_diff`（两期栅格类别转换矩阵 + 连通斑块）
- **明确边界**：6 个月窗口的短周期变化；提供线索不做违建认定

### 场景 C：高硬化低绿地压力与补绿优先区——建评分/排序层（面向决策）

- **用户问法**："哪些片区硬化率高、绿地率低？" / "哪里适合优先补绿？" / "生成压力分布图"
- **数据流**：复用 A 的聚合统计 + B 的变化趋势 → 格网/patch 级复合评分（硬化率↑ + 绿地率↓ + 距水体绿块远 + 近期硬化仍在增加加权）→ 压力分级图 + **补绿/透水化改造优先区清单**
- **报告主语**：压力 TOP-N 区域排名 + 每区"为什么上榜"（数据依据）+ 行动建议——直接服务城市更新/花园城市叙事
- **建成工具**：`score_rank`（多因子加权评分，权重可配置）
- **明确边界**：热岛为代理指标（无热红外反演）；评分是初筛不是工程结论

**递进关系**：A 建聚合 → B 建变化 → C 组合评分。做完三者，能力边界文档其余场景均为工具重组。

## 5. 分阶段开发计划

| 阶段 | 内容 | 交付物 / 验收 | 预估 |
| --- | --- | --- | --- |
| **P0 架构加固**（先行） | ① `taxonomy.py` 词表收敛（G5）② 数据访问层：统一 HTTP client 基类（重试/超时/缓存）并迁移三区域 service ③ 结构化日志 + run 级追踪 ④ systemd 单元 + SQLite WAL + 健康探测增强 | 行为零变化（现有 54 项测试全绿 + 回归批测）；`journalctl` 可查每次 run 的路由轨迹；kill -9 后 10s 内自动拉起 | ~1 周 |
| **P1 工具层地基** | ① `class_map`：海淀 PNG 颜色→类别映射（依赖 D1，见 §6）② `aoi_cover` + `raster_stats`：AOI→patch 集→裁剪聚合→公顷换算 ③ skill/tool 注册表骨架 + planner 节点（规则选 skill） | 纯函数单测覆盖；给定固定 AOI，面积统计可复现且与手工核算误差 <1% | 1~1.5 周 |
| **P2 场景 A 上线** | `region_checkup` skill + 体检报告模板（面积/占比主语）+ 意图路由（"体检/绿地率/硬化率"类问法） | 框选任一海淀 AOI → 一句话生成体检报告；批测问法 ≥10 条无误路由 | ~1 周 |
| **P3 场景 B 上线** | `change_diff` tool + `change_monitor` skill + 两期对比意图（"最近半年变化/对比12月和5月"） | 指定 AOI 两期对比报告：变化斑块图 + 转换矩阵 + 面积清单 | 1~1.5 周 |
| **P4 场景 C 上线** | `score_rank` tool + `priority_rank` skill + 压力/优先区报告 | "哪里该优先补绿" → TOP-N 清单报告，每项带数据依据 | ~1 周 |
| **P5 演进预留** | skill 选择升级为 LLM function-calling；web_search tool 试点；外部数据 adapter 设计评审 | 设计文档 + 原型 | 后续排期 |

> 每阶段结束：跑全量 pytest + 回归批测（对话边界 25 例 + 各场景问法），更新 `agent/API.md` 与 `CLAUDE.md`，可独立上线。

## 6. 风险与依赖

| # | 风险/依赖 | 影响 | 对策 |
| --- | --- | --- | --- |
| D1 | **海淀 PNG 图例缺失**（G3）：颜色→类别映射需 embedding-api 方提供图例，或我们对已知样本人工标定颜色表 | P1 起点 | 双轨：先与数据方要图例元数据；同时对 6 色样本人工比对标定并固化为配置，接口就绪后切换 |
| D2 | embedding-api 可用性（曾出现整段拒连） | 场景全链路 | 数据访问层缓存已取 PNG；离线时用缓存降级 + 友好提示 |
| D3 | 6 个月窗口的"变化"叙事偏弱 | 场景 B 价值感 | 话术定位"短周期建设扰动监测"；月内多期数据可做更细粒度序列；雅江多年数据留作"变化能力"的第二示范区 |
| D4 | AOI 跨 patch 拼接的边缘效应/重叠处理 | 面积精度 | P1 以"patch 并集裁剪 AOI"起步并声明估算口径；精细镶嵌后续优化 |
| D5 | 多 worker 与 SQLite 并发 | P0 | 开 WAL + busy_timeout；如仍瓶颈，memory 层已收口、可平滑换存储 |
